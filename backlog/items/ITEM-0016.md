# ITEM-0016: Implement AEAD encryption and decryption for encrypted envelopes

## Why

Symmetric encryption of blobs is the core operation of the system. Unauthenticated
encryption (AES-CBC, AES-CTR without a MAC) allows ciphertext tampering without
detection. Reusing nonces under the same key breaks confidentiality for XChaCha20.
The implementation must use a cryptographically secure random nonce per encryption
call and an AEAD construction that provides both confidentiality and integrity.

## Scope

- Implement `encrypt(plaintext, key, associatedData?): Promise<EncryptedEnvelope>`
  using XChaCha20-Poly1305 (or the AEAD algorithm confirmed by ITEM-0012/0013)
- Implement `decrypt(envelope, key, associatedData?): Promise<Uint8Array>`
- Nonce is generated by `randomBytes(24)` per call — not stored externally
- Unit tests for all five acceptance criteria

## Out of scope

- Key derivation — that is ITEM-0018 and ITEM-0019
- Envelope serialisation to bytes — that is ITEM-0024
- Stream or chunked encryption

## Constraints

- Blocked by ITEM-0014 and ITEM-0013
- Must use the algorithm selected in ITEM-0013 ADR
- Nonces must never be reused; implementation must not accept nonce as a parameter

## Decisions and rejected alternatives

- Chose XChaCha20-Poly1305 over AES-GCM because XChaCha20 uses a 192-bit nonce
  making random nonce collision probability negligible even at high message volumes;
  AES-GCM's 96-bit nonce requires counter-based generation at scale
- Rejected exposing raw encrypt/decrypt without AEAD to avoid silent data corruption
