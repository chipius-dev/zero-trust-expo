# ITEM-0033: Design incremental sync protocol with optimistic concurrency

## Why

Without a committed sync protocol design, the implementation will invent its own wire
format, conflict model, and offline queue — each of which will diverge across
platforms. The design document establishes the contract before any sync code is
written, so the server and client agree on the sequence number semantics and the
conflict resolution policy.

## Scope

- Sequence diagram: GET /sync?since=N, server returns events since N, client applies
- Optimistic write: client sends (object_id, ciphertext, expected_sequence_number),
  server rejects with 409 if server sequence > expected
- Offline queue: local ring buffer of pending writes, replayed on reconnect in order
- Conflict policy decision: last-write-wins (initial scope) or flag and defer
- Document what the server sees vs. what it cannot see in a sync request

## Out of scope

- WebSocket or server-sent events (polling is the initial scope)
- CRDT or operational transform merge
- Sync between different accounts

## Constraints

- Blocked by ITEM-0028 (sequence_number schema must exist) and ITEM-0021 (auth
  state drives which account's objects are synced)
- Server must not see plaintext object semantics in any sync request or response

## Decisions and rejected alternatives

- Chose sequence-number-based incremental sync over full vault download because vault
  size grows unbounded; full download is impractical after the first sync
- Chose last-write-wins as the initial conflict policy over client-choice merge
  because LWW is deterministic, requires no application-domain knowledge on the
  server, and handles the common single-user multi-device case correctly
