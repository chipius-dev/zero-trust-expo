# ITEM-0037: Document and validate metadata privacy mitigations

## Why

Perfect metadata privacy is impossible: the server observes IP addresses, event
timing, ciphertext sizes, and object counts. Claiming otherwise is dishonest. The
architecture should explicitly catalogue what leaks, why it is unavoidable, and what
mitigations reduce the inference. Failing to document leakage leads to users or
auditors falsely believing the system provides stronger privacy than it does.

## Scope

- Metadata privacy analysis document in docs/architecture/
- Catalogue: account existence, authentication events, IP addresses, timestamps,
  ciphertext sizes, object counts, device count, update frequency, sync patterns,
  attachment sizes, deletion events
- Per-leakage entry: leakage type, what the server can infer, which mitigation is
  implemented (opaque IDs, padding, batching, minimised timestamps), remaining leakage
- Distinction between content confidentiality (ciphertext is opaque) and metadata
  confidentiality (access patterns are visible)
- Validate opaque identifier claims: confirm no SELECT can return an email or username

## Out of scope

- Implementing new mitigations beyond those already in scope for other stories
- Network-level anonymisation (Tor, VPN)
- Differential privacy for access patterns

## Constraints

- Blocked by ITEM-0026 (padding) and ITEM-0027-0029 (schema) being complete
- Must not claim mitigations that are not implemented

## Decisions and rejected alternatives

- Chose to document leakage explicitly over omitting it because omission creates false
  assurance; an honest threat analysis is more useful than an optimistic one
- Rejected adding metadata obfuscation mechanisms (e.g., dummy writes) until the
  primary architecture is proven correct
