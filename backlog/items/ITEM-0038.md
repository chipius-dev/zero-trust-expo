# ITEM-0038: Validate Expo managed workflow and Hermes compatibility

## Why

The Expo managed workflow imposes constraints that are invisible in Node.js testing:
Hermes has a different JS engine feature set (no `wasm` module system, restricted
`TextEncoder` availability in older versions, no `crypto.subtle` before RN 0.71).
A library that passes CI in Node.js may silently fail on Hermes. This story produces
verified evidence, not assumptions.

## Scope

- Set up a minimal Expo test app (or test harness) that runs the CryptoProvider
  against a Hermes engine
- Execute each primitive: randomBytes, hashPassword, encrypt, decrypt, deriveSubkey
- Document any Metro bundler config changes required (WASM mime type, asset extensions)
- Document any Expo config plugin additions (if native module is required)
- Produce a Markdown report committed to docs/architecture/expo-compatibility.md

## Out of scope

- Full Expo app with UI — this is a technical validation, not an application
- App Store or Google Play submission

## Constraints

- Blocked by ITEM-0014 through ITEM-0017 (CryptoProvider must be implemented)
- Must test against the Hermes version shipped with the Expo SDK version in use
- If compatibility fails, produce a remediation plan rather than silently skipping

## Decisions and rejected alternatives

- Chose to run actual Hermes validation over reading the library's documentation
  because documentation may lag behind actual engine compatibility
- Rejected combining this with ITEM-0039 because CI/CD documentation is a distinct
  deliverable from engine compatibility testing
