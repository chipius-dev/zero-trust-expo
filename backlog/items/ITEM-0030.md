# ITEM-0030: Implement device enrollment with encrypted key transfer

## Why

A new device needs the vault key to decrypt stored objects. Transmitting the vault key
through the server collapses the zero-trust boundary. The correct approach: the
enrolling device wraps the vault key to the new device's public key; the new device
unwraps it locally. The server stores only the wrapped (encrypted) key and never sees
the plaintext vault key.

## Scope

- New device: `generateDeviceKeyPair(): Promise<{ publicKey, privateKey }>`
- Enrolling device: `wrapVaultKeyForDevice(vaultKey, devicePublicKey): Promise<Uint8Array>`
- New device: `unwrapVaultKey(wrappedKey, devicePrivateKey): Promise<CryptoKey>`
- Server API call stubs to register the device and store the wrapped vault key
- Tests proving the vault key never appears in the wrapped key bytes for a random guess

## Out of scope

- Recovery flow when no enrolling device is available — that is ITEM-0032
- Device revocation — that is ITEM-0031
- UI for enrollment approval on the enrolling device

## Constraints

- Blocked by ITEM-0019 (subkey derivation for the device-wrap key purpose) and
  ITEM-0029 (devices schema must exist)
- Private key must never leave the device; not stored server-side, not in the database

## Decisions and rejected alternatives

- Chose X25519 ECDH key exchange to derive a shared secret for wrapping the vault key
  over transmitting the vault key directly, so the server stores only opaque ciphertext
- Rejected requiring QR code out-of-band confirmation in this story; it is a UX
  concern deferred to a later story
