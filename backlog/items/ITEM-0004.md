# ITEM-0004: Key Hierarchy and Derivation

## Why

Without a formal key hierarchy, developers will reuse keys across purposes (using the
vault key also as the sync key, or the master key directly for encryption). Key reuse
collapses the security boundary between subsystems: a vault key disclosure also
compromises sync state. There is also no rotation path: without versioned, purpose-
specific keys, rotating after a breach requires re-encrypting all data with a new
root key derived from a new password.

## Scope

- Document the full key hierarchy: Password → Argon2id → master key → purpose-specific
  subkeys (vault key, sync key, attachment key, device key, recovery key)
- Specify domain separation strings for each purpose
- Implement `deriveSubkey(masterKey, purpose, version)` with a test proving different
  purposes produce different keys from the same master key
- Implement key rotation: re-derive subkeys at the next version, re-encrypt affected
  data, confirm old subkeys are no longer used
- Define key metadata schema: purpose, version, algorithm, derivation context,
  lifecycle state

## Out of scope

- Persisting keys to disk or device keychain — that is ITEM-0008
- Password change and authentication protocol — that is ITEM-0005
- Key transfer to a new device — that is ITEM-0008

## Constraints

- Blocked by ITEM-0003 (CryptoProvider interface must exist)
- Derivation must use the library's HKDF or equivalent, not a hand-rolled KDF
- Domain separation strings must be globally unique within the application

## Decisions and rejected alternatives

- Chose purpose + version domain separation over separate Argon2id calls per purpose
  because Argon2id is deliberately slow; deriving the master once and branching via
  fast HKDF is the standard pattern
- Rejected deriving vault and sync keys from different passwords because password
  changes must rotate all derived material in one operation
