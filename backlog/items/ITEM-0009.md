# ITEM-0009: Synchronization Engine

## Why

Without an offline-capable sync engine, the application requires a live server
connection for every read and write, making it unusable in low-connectivity
environments. Without optimistic concurrency control, concurrent writes from two
devices silently overwrite each other. Without an encrypted event log, the server
observes write patterns and the relationship between objects and updates.

## Scope

- Incremental sync protocol: GET changes since sequence N, client decrypts and applies
- Encrypted sync event log: event payloads are ciphertext; server sees only sequence
  number, timestamp, and opaque object_id
- Optimistic concurrency: each encrypted object carries a version/sequence counter;
  writes include the last-known version and fail with a conflict if the server has a
  higher version
- Conflict detection and resolution policy (last-write-wins or client-side merge)
- Offline queue: local writes buffered and replayed on reconnect
- Encrypted snapshots for efficient initial sync on a new device

## Out of scope

- Real-time push (WebSocket / server-sent events) — polling is sufficient initially
- Operational transform or CRDT-based merge — last-write-wins with conflict detection
  is the initial scope
- Sync between vaults belonging to different accounts (sharing)

## Constraints

- Server must not understand event semantics; sync protocol is blind to domain model
- Blocked by ITEM-0006 (encrypted blob model) and ITEM-0007 (schema)
- Conflict resolution must be deterministic and testable offline

## Decisions and rejected alternatives

- Rejected storing plaintext event summaries on the server for search/query because
  the server is untrusted; the client holds the domain model
- Chose sequence-number-based incremental sync over full-vault-download on each sync
  because full downloads are prohibitive as vault size grows
