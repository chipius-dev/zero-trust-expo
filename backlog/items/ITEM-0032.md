# ITEM-0032: Implement lost device recovery flow

## Why

A user who loses all trusted devices and has no recovery key is permanently locked
out of their vault. The recovery key is the offline paper backup that breaks the
impasse: it is derived from the master key hierarchy (not a separate secret) so it
can be reconstructed from the password, but is designed to be printed or written and
stored offline.

## Scope

- `deriveRecoveryKey(masterKey): Promise<Uint8Array>` — deterministic from master key
- `exportRecoveryPhrase(recoveryKey): string` — human-readable BIP-39-style word list
- `recoverVaultFromPhrase(phrase, password): Promise<CryptoUnlockState>`
- Tests for each acceptance criterion; test that recovery does not require a server
  call beyond authentication

## Out of scope

- Secure element / hardware recovery (FIDO2) — future epic
- Social recovery (trusted contacts) — out of scope for this architecture

## Constraints

- Blocked by ITEM-0019 (deriveSubkey must exist for recovery purpose)
- Recovery key must be derived from the master key, not stored independently — so a
  password change automatically invalidates the old recovery key
- Recovery phrase must be invalidated after single use to prevent replay

## Decisions and rejected alternatives

- Chose deterministic derivation from master key over a separately generated random
  recovery key because a separate random key requires its own backup problem; the
  master key already incorporates the password as entropy
- Rejected storing the recovery key server-side because the server is untrusted; the
  recovery path must work even if the server is compromised
