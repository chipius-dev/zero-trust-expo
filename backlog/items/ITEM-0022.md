# ITEM-0022: Evaluate and select password authentication protocol

## Why

There are multiple standardised password-authentication protocols. Choosing incorrectly
(e.g., sending H(password) as auth credential when it is also derivable into the vault
key) breaks the separation documented in ITEM-0021. OPAQUE provides a stronger
guarantee than SRP-6a but has fewer production implementations; the trade-off must
be evaluated before code is written.

## Scope

- Research OPAQUE (RFC draft), SRP-6a, and simple hash-over-TLS
- For each: server-side state leakage, implementation availability in the target JS
  stack, library maturity, and compliance with the zero-trust constraint
- Decision and ADR using templates/adr-template.md

## Out of scope

- Implementing the chosen protocol — that is ITEM-0023
- OAuth or social login

## Constraints

- Blocked by ITEM-0021 (separation documented before protocol is selected)
- Must not invent a custom protocol; must use a standardised scheme

## Decisions and rejected alternatives

- Decision between OPAQUE and SRP-6a is explicitly deferred to this story so that
  the choice is evidence-based rather than assumed
