# ITEM-0003: Crypto Abstraction Layer

## Why

Without a stable TypeScript interface, application code will couple directly to the
selected library's API. Any future library swap requires touching every callsite, and
different developers can make different assumptions about nonce management, key
encoding, or associated data — creating subtle security bugs that are invisible to
reviewers unfamiliar with the underlying library.

## Scope

- Define the `CryptoProvider` TypeScript interface and all supporting types
  (PasswordVerifier, CryptoKey, EncryptedEnvelope, KeyPurpose)
- Implement `hashPassword` and `verifyPassword` using Argon2id via selected library
- Implement `encrypt` and `decrypt` using XChaCha20-Poly1305 AEAD
- Implement `randomBytes` with secure random generation on every target platform
- Implement `deriveMasterKey` and `deriveSubkey` with domain-separated contexts
- Write unit tests asserting the interface contract (not the library internals)

## Out of scope

- Key hierarchy design and lifecycle rules — that is ITEM-0004
- Authentication protocol and session management — that is ITEM-0005
- Platform-specific native module packaging — that is ITEM-0011

## Constraints

- Blocked by ITEM-0002 (library selection ADR must exist before implementation)
- Interface must be serialisation-format-stable: EncryptedEnvelope must be versioned
- No library types may leak through the interface boundary

## Decisions and rejected alternatives

- Chose a flat functional interface over a class hierarchy because the interface is
  injected, not extended, and class hierarchies encourage consumers to import concrete
  types rather than the abstraction
- Rejected re-exporting library types because that would couple consumers to the
  library directly
