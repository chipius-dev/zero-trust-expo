# ITEM-0021: Design auth flow separating credential check from crypto unlock

## Why

Conflating authentication with cryptographic unlock is the most common architectural
mistake in password-protected systems. If the session token can unlock the vault,
a stolen session token breaks confidentiality even though the server never received
the password. The design document makes the boundary explicit and reviewable before
any authentication code is written.

## Scope

- Sequence diagram: account creation flow, login/unlock flow, lock-without-logout
- TypeScript interfaces: `AuthState` (token, expiry, accountId), `CryptoUnlockState`
  (in-memory derived keys, never persisted to server)
- Document: what happens on session expiry (re-authenticate without re-deriving keys
  if masterKey still in memory), what happens on app backgrounding (zero memory)
- Written rationale for why the two states must never be conflated

## Out of scope

- Implementation of any auth endpoint or session management
- MFA or OPAQUE protocol selection — that is ITEM-0022
- Device key transfer — that is ITEM-0030

## Constraints

- Blocked by ITEM-0013 (library selection complete)
- Diagrams must be in a format that renders in GitHub Markdown (Mermaid preferred)

## Decisions and rejected alternatives

- Rejected a single `UserSession` type that combines auth token and derived keys
  because it creates the conflation this story is designed to prevent
- Chose sequence diagram over prose because the ordering of steps (auth before unlock,
  unlock is local-only) is the critical property and prose descriptions are ambiguous
