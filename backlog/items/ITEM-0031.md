# ITEM-0031: Implement device revocation and post-revocation key rotation

## Why

Revoking a device from the server session is insufficient: the revoked device retains
a copy of the vault key and can continue to decrypt all objects. Cryptographic
revocation requires rotating the vault key and re-encrypting all stored objects so
that possession of the old key provides no ongoing access.

## Scope

- `revokeDevice(deviceId, vaultKey): Promise<void>` — inserts tombstone, rotates key
- Key rotation: derive a new vault key at the next version (ITEM-0019 pattern)
- Re-wrap the new vault key for all non-revoked devices
- Re-encrypt all encrypted_objects rows with the new vault key
- Unit tests for each acceptance criterion; integration test for the full rotation path

## Out of scope

- Network enforcement (rate limiting revoked device_id) — server concern
- Key rotation without device revocation — separate story under ITEM-0040

## Constraints

- Blocked by ITEM-0030 (enrollment must exist before revocation is meaningful)
- Re-encryption must be atomic from the server's perspective or use a versioned
  migration that leaves old ciphertext readable during transition

## Decisions and rejected alternatives

- Chose full re-encryption over marking old blobs inaccessible to the revoked device
  because the revoked device already has a local copy of the vault contents; the only
  protection is that future writes are encrypted with a key it cannot derive
- Rejected lazy rotation (re-encrypt only on next write) because stale reads remain
  accessible to the revoked device indefinitely under lazy rotation
