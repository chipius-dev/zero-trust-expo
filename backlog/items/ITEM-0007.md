# ITEM-0007: Privacy-Preserving SQLite Schema

## Why

A naive schema exposes account identifiers (email, username), object types, and
relationships as plaintext in server-visible columns. Even with encrypted payloads,
a compromised database reveals the structure of a user's vault, the frequency of
writes, and the types of objects stored — sufficient for significant inference about
user behaviour.

## Scope

- Accounts table with opaque random identifiers (never email or username)
- Auth credential storage (password verifier material, not the password)
- Sessions and device registration tables
- Encrypted objects table: opaque object_id, ciphertext column, key version,
  sequence number for optimistic concurrency
- Object versions table for history and conflict resolution
- Sync events table with encrypted event payloads
- Tombstone/revocation table for deleted objects and revoked devices
- Field-level annotation of each column as SERVER MUST KNOW / MAY KNOW / MUST NEVER KNOW
- Migration versioning table

## Out of scope

- ORM or query layer code; this epic delivers SQL DDL only
- Application-layer queries and access patterns
- Database encryption at rest (separate storage concern)
- Full-text search over encrypted content

## Constraints

- Must be SQLite-compatible
- Opaque identifiers must be cryptographically random (not sequential integers)
- Indexes must be minimised; each index must be justified given metadata privacy impact
- Schema changes must be expressed as additive migrations (no destructive ALTER TABLE)

## Decisions and rejected alternatives

- Chose random UUID-type identifiers over sequential IDs because sequential IDs expose
  the order and rate of account creation and object insertion
- Rejected storing email in the accounts table; email belongs in an auth credential
  row with a one-way hash used only for lookup, never exposed in queries
