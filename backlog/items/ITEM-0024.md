# ITEM-0024: Define versioned encrypted envelope specification

## Why

Without a committed binary format specification, each platform will serialise the
envelope differently. iOS might use base64 with one field ordering; Android might use
a different struct layout. A stolen database of ciphertext is meaningless if no
platform can deserialise and decrypt it. Cross-platform interoperability requires a
single canonical format that all implementations follow.

## Scope

- Markdown spec document: field list (envelope version, algorithm ID, key version,
  nonce, ciphertext length, ciphertext, Poly1305 tag, associated data)
- Byte-level layout: big-endian field sizes, alignment, length prefixing
- Versioning: how a reader identifies and handles an unknown version
- Associated data construction: what fields are included, in what order, to
  authenticate the envelope metadata alongside the ciphertext
- A worked hex example

## Out of scope

- Implementation code — that is ITEM-0025
- Compression format selection — deferred; the spec reserves a flag bit

## Constraints

- Blocked by ITEM-0013 (algorithm must be selected before field widths are fixed)
- Format must be stable from the first commit; migration requires a new version byte

## Decisions and rejected alternatives

- Chose a binary format over JSON envelope because JSON encoding of binary fields
  (base64) adds 33% overhead and introduces encoding ambiguity across platforms
- Rejected using the library's built-in serialisation because it may not be stable
  across library versions
