# ITEM-0006: Encrypted Blob Storage Model

## Why

Without a well-defined pipeline from domain model to opaque ciphertext, developers
will leak semantics to the server (storing object type as a column, object name as
a field, or metadata as indexed values). The server must receive only opaque encrypted
envelopes: it must not be able to distinguish between a password record, a health
record, or a document.

## Scope

- Versioned EncryptedEnvelope wire format specification (header, nonce, ciphertext,
  tag, associated data, key version, algorithm identifier)
- Pipeline implementation: domain model → canonical JSON → optional compression →
  AEAD encrypt → EncryptedEnvelope
- Ciphertext padding strategy to reduce size-based metadata leakage
- Serialisation and deserialisation with schema migration hooks for future versions
- Tests confirming envelope round-trips and that tampering with any field causes
  decryption to fail

## Out of scope

- The server storage schema for envelopes — that is ITEM-0007
- Attachment/binary blob handling beyond the core envelope format
- Compression algorithm selection (defer to implementation story)
- Key hierarchy for selecting which key encrypts which object type — that is ITEM-0004

## Constraints

- Blocked by ITEM-0003 (CryptoProvider must exist)
- Envelope format must be stable and versioned from day one; migrations must be
  mechanical without requiring full vault decryption

## Decisions and rejected alternatives

- Chose opaque server-side storage over domain-typed server records because the server
  is in the threat model; semantic columns leak type information even if values are
  encrypted
- Rejected streaming encryption (e.g., ChaCha20 without authentication) because
  authenticated encryption is non-negotiable for integrity
