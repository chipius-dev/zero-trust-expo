# ITEM-0005: Authentication Protocol and Account Model

## Why

Authentication (proving identity to the server) must be completely decoupled from
cryptographic unlock (deriving the key to decrypt the user's vault). Conflating the
two means: (a) the server learns the password or master key during login, violating
the zero-trust boundary; (b) a session token cannot independently expire without
also invalidating the user's vault access.

## Scope

- Design and document the separation between authentication state and cryptographic
  unlock state (client-side only)
- Evaluate OPAQUE (PAKE-based) vs SRP-6a vs password-hash-over-TLS as authentication
  options; record the decision in an ADR
- Define the account creation flow (identity registration without revealing the
  password to the server)
- Define the login/unlock flow (authenticate then derive vault keys locally)
- Define the PasswordVerifier format stored server-side (opaque to the server, reveals
  no key material)
- TypeScript interfaces for session and account state

## Out of scope

- Actual server implementation of the auth endpoints
- OAuth/SSO — this architecture uses a first-party credential model
- Multi-factor authentication (may be added as a separate story later)
- Device enrollment and key transfer — that is ITEM-0008

## Constraints

- Must not transmit the password or any key material to the server during auth
- Must not invent a custom authentication protocol; must use a standardised scheme
- Blocked by ITEM-0002 and ITEM-0003

## Decisions and rejected alternatives

- Rejected transmitting H(password) to the server and using it as an encryption key,
  because then the password hash itself becomes the encryption key and server
  disclosure breaks both authentication and confidentiality simultaneously
- The decision between OPAQUE and SRP-6a is deliberately deferred to the ITEM-0022
  story to allow evidence-based evaluation
