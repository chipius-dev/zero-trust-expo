# ITEM-0026: Implement ciphertext padding strategy for metadata privacy

## Why

Even with perfect encryption, ciphertext size leaks information: a 16-byte blob is
likely a short password, a 4096-byte blob is likely a document. An adversary
observing the database can cluster objects by type using size alone. Padding to fixed
buckets reduces this inference without revealing the actual content size.

## Scope

- Padding function: `padToNextBucket(plaintext: Uint8Array, buckets: number[]): Uint8Array`
- Default bucket sizes: [64, 128, 256, 512, 1024, 4096, 16384, 65536] bytes
- Strip padding on decrypt
- Document the bucket sizes and the information they leak (sizes above 64KB are still
  distinguishable by count, not bucket)
- Unit tests for all four acceptance criteria

## Out of scope

- Padding of attachment binary data (separate story)
- Network-level padding (separate transport concern)

## Constraints

- Blocked by ITEM-0024 (envelope spec must include a plaintext-length field so the
  decoder knows where padding begins)
- Bucket sizes must be configurable, not hardcoded to constants

## Decisions and rejected alternatives

- Chose power-of-two buckets over fixed 64-byte block padding because very small
  fixed block sizes (PKCS7-style) still reveal an approximate plaintext length, while
  exponential buckets cap the maximum size leakage to one bit per bucket boundary
- Rejected randomised padding because it makes size non-deterministic and complicates
  conflict detection in sync
