# ITEM-0040: Implement key rotation for vault and sync keys

## Why

Key rotation is the response to a subkey compromise that does not involve the master
key or password. Without rotation, a disclosed vault key provides indefinite access
to all historical and future vault data. With rotation, a disclosed key covers only
the data encrypted under that key version; data re-encrypted under the new version
is protected.

## Scope

- `rotateVaultKey(currentVaultKey, masterKey): Promise<CryptoKey>` — derives the next
  version key using ITEM-0019 `deriveSubkey` with incremented version number
- Re-encrypt all `encrypted_objects` rows in batches (to avoid a single giant
  transaction that could time out on large vaults)
- Update `key_version` column per row on completion
- Atomic failure handling: if rotation is interrupted, incomplete rows remain at the
  old version and are re-encrypted on the next rotation attempt
- Unit tests and an integration test covering all five acceptance criteria

## Out of scope

- Password change and master key rotation — that requires re-running Argon2id and is
  a separate story under ITEM-0005
- Rotation triggered by device revocation — that is ITEM-0031

## Constraints

- Blocked by ITEM-0019 (deriveSubkey) and ITEM-0028 (key_version column in schema)
- Rotation must not leave any object in an unreadable state at any point

## Decisions and rejected alternatives

- Chose incremental batch re-encryption over a single transaction because SQLite can
  lock the database for the duration of a large transaction, blocking reads and sync
- Rejected a copy-then-delete approach (write re-encrypted rows to a new table then
  swap) because it doubles disk usage during rotation, which is prohibitive on mobile
