# ITEM-0008: Device Trust and Enrollment

## Why

Without a device trust model, adding a second device forces the user to re-enter
their password and re-derive all keys from scratch, or — worse — transmit key
material through the server. A revoked device (lost phone, stolen laptop) must
be cryptographically excluded, not merely logged out. Without revocation,
possession of a stale session token or a copy of the local database is sufficient
to decrypt the user's vault indefinitely.

## Scope

- Device identity: per-device asymmetric key pair (Ed25519 or X25519)
- Device enrollment flow: new device generates its key pair, existing trusted device
  (or recovery path) wraps the vault key for the new device
- Encrypted key transfer: vault key is AEAD-encrypted to the new device's public key
  and stored server-side; server never sees the plaintext key
- Device revocation: tombstone record, key rotation, re-encryption of key transfer
  records for remaining trusted devices
- Lost-device recovery: recovery key derived from master key hierarchy unwraps the
  vault key without requiring another trusted device
- Password change propagates: new master key re-wraps all per-device key transfers

## Out of scope

- Hardware security key (FIDO2/WebAuthn) — may be a future epic
- Device attestation (SafetyNet, DeviceCheck) — abuse prevention, not this epic
- Multiple users per vault — single-user model only

## Constraints

- Blocked by ITEM-0004 (key hierarchy must exist)
- Server must never receive plaintext vault key material
- Revocation must be cryptographic, not merely session-based

## Decisions and rejected alternatives

- Rejected server-assisted key escrow because the server is untrusted; server escrow
  means server compromise reveals all vault keys
- Rejected requiring a trusted device for recovery because users lose all devices;
  the recovery key derived from the password hierarchy is the fallback
