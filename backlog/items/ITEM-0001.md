# ITEM-0001: Zero-Trust Cross-Platform Cryptographic Architecture

## Why

Applications built on Expo + React Native today have no standardised cryptographic
foundation. Teams reach for ad-hoc solutions (insecure storage, server-side encryption,
rolling their own key management) or simply skip encryption. A server compromise in any
of those architectures directly exposes user data. This initiative builds a
production-grade architecture in which the server is explicitly untrusted: it stores
only opaque ciphertext and cannot decrypt user data even if fully compromised.

## Scope

- Cryptographic library selection (evidence-based, cross-platform)
- TypeScript CryptoProvider abstraction and encrypted envelope format
- Client-side key hierarchy (password → Argon2id → purpose-specific subkeys)
- Authentication protocol design (credential verification ≠ cryptographic unlock)
- Encrypted blob storage model (domain model → AEAD ciphertext → opaque server record)
- Privacy-preserving SQLite schema (opaque IDs, ciphertext-only columns)
- Device trust: enrollment, revocation, key transfer, recovery
- Offline-capable incremental synchronisation with conflict detection
- Security tests proving cross-platform interoperability and database compromise bounds
- Expo / React Native integration requirements and Hermes compatibility

## Out of scope

- Application-specific domain models (passwords, notes, financial records)
- Backend server implementation code (only the schema and API contract)
- UI or UX components
- Third-party SaaS integrations
- Certificate pinning and transport-layer concerns
- Hardware security module (HSM) key management

## Constraints

- Must run on Web, PWA, iOS, Android, macOS, Windows, Linux without platform-specific
  cryptographic formats
- Expo managed workflow compatible; Hermes runtime compatible
- No hand-rolled cryptographic primitives; only audited, actively maintained libraries
- WIP limit of 3 concurrent in-progress items across the whole repo
- Items land one story per branch, one review

## Decisions and rejected alternatives

- Chose client-side zero-trust over server-side encryption because the server is in
  the threat model; server-side key management (HSM, KMS) protects against
  infrastructure attackers but not against a compromised or malicious operator.
- Chose a unified JS/TS crypto library over native bindings on each platform because
  the goal is a single codebase with identical ciphertext formats across all seven
  targets; native-only libraries require platform-specific maintenance.
- Rejected splitting the architecture into separate web and native stacks because
  divergent implementations produce divergent ciphertext formats, breaking
  cross-platform decrypt.
