# ITEM-0002: Cryptographic Library Evaluation

## Why

No cryptographic library has been selected. Choosing a library that lacks genuine
cross-platform support means some platforms will require custom native modules,
diverge in ciphertext format, or lack the specific primitives (Argon2id,
XChaCha20-Poly1305, X25519, Ed25519) that the architecture requires. The wrong
choice surfaces as a hard migration during later epics, not at the decision point.

## Scope

- Identify and document candidate JS/TS cryptographic libraries
- Evaluate each against: Web, PWA, iOS, Android, macOS, Windows, Linux support;
  Expo managed and development build compatibility; Hermes compatibility; TypeScript
  API quality; audit history; active maintenance; WASM/native dependency surface
- Produce a compatibility matrix covering all seven target platforms × required
  cryptographic capabilities
- Select a primary library and write an ADR recording the decision
- Identify a minimal compatibility shim if no single library fully covers all targets

## Out of scope

- Implementing any wrapper code or provider — that is ITEM-0003
- Performance micro-benchmarking beyond basic feasibility
- Server-side library selection

## Constraints

- Decision must be recorded in an ADR before any ITEM-0003 work begins
- Must evaluate at least: libsodium.js / libsodium-wasm, @noble/ciphers +
  @noble/hashes + @noble/curves, and native WebCrypto API coverage
- Library must support Argon2id, XChaCha20-Poly1305, X25519, and Ed25519

## Decisions and rejected alternatives

- Rejected evaluating proprietary or source-unavailable libraries because security
  audit history must be publicly verifiable
- Rejected selecting a library on feature breadth alone; smallest trustworthy
  cryptographic surface wins over largest feature set
