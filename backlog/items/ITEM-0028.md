# ITEM-0028: Define server API contract request and response types

## Why

The API contract types are the line that must not be crossed: everything on the
server-facing side of these types must be opaque (IDs and ciphertext); everything
on the client-facing side can be richly typed domain objects. Without explicit
typed boundaries, a developer will accidentally add a `type` or `name` field to
a request body — leaking semantics to the server — because there is no type error
to stop them.

## Scope

- Auth: `CreateAccountRequest`, `CreateAccountResponse`, `LoginRequest`,
  `LoginResponse`, `RefreshSessionRequest`, `RefreshSessionResponse`
- Objects: `PutObjectRequest` (opaque ID + ciphertext + key version + sequence),
  `PutObjectResponse` (new sequence), `GetObjectResponse`, `ListObjectsRequest`
  (cursor + since-sequence), `ListObjectsResponse`
- Devices: `RegisterDeviceRequest`, `RegisterDeviceResponse`,
  `RevokeDeviceRequest`, `RevokeDeviceResponse`
- Sync: `GetSyncEventsRequest` (since-sequence), `GetSyncEventsResponse`
  (array of `SyncEventEnvelope`)
- All request/response types live in a single `api-contract.ts` with no storage or
  crypto library imports

## Out of scope

- HTTP client implementation or fetch wrappers
- Error type modelling (a separate concern)
- Any server-side routing or handler types

## Constraints

- Blocked by ITEM-0027 (entity types) and ITEM-0024 (envelope format)
- No field named `type`, `name`, `category`, `email`, or `username` on any type
  that crosses the client–server boundary

## Decisions and rejected alternatives

- Chose explicit per-endpoint request/response types over a generic `ApiRequest<T>`
  wrapper because generic wrappers make it easy to accidentally pass domain objects
  as the type parameter, bypassing the opaque-only constraint
- Rejected OpenAPI/JSON Schema generation in this story — it is a future concern
  that can be derived from these types; locking to a generator tool now would
  add a dependency the template doesn't need
