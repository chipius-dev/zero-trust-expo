# ITEM-0028: Design encrypted objects and object versions schema

## Why

The encrypted objects table is where all vault ciphertext lives. Any semantic column
in this table (type, name, category) immediately reveals object structure to an
adversary with database access. The table must look like a namespace of opaque blobs
to any party without the vault key.

## Scope

- `encrypted_objects` table: object_id (opaque UUID), account_id, ciphertext (BLOB),
  key_version, sequence_number, created_at, updated_at, deleted_at (tombstone)
- `object_versions` table: version_id, object_id, ciphertext snapshot, sequence_number
- No type, category, name, or any domain-semantic column
- Column-level privacy annotations
- Rationale for each index (sequence_number index for sync is justified)

## Out of scope

- Attachment/binary large object storage (separate story)
- Client-side object model or query API

## Constraints

- Blocked by ITEM-0027 (accounts schema must exist to define account_id reference)
- Blocked by ITEM-0024 (envelope spec determines what goes in the ciphertext column)
- No columns that reveal object semantics to the server

## Decisions and rejected alternatives

- Chose a unified `encrypted_objects` table for all object types over per-type tables
  (passwords, notes, documents) because per-type tables reveal type information to a
  database adversary
- Rejected storing object metadata (created by, shared with) in plaintext columns;
  such metadata belongs inside the encrypted payload if it is needed at all
