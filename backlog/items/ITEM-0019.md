# ITEM-0019: Implement purpose-specific subkey derivation from master key

## Why

All subkeys share one root (the master key). Without correct domain separation in
HKDF info, two purposes could receive the same subkey bytes, collapsing their
security boundaries. The vault key and sync key must be provably independent.

## Scope

- Implement `deriveSubkey(masterKey, purpose, version): Promise<CryptoKey>` using
  HKDF (or the library equivalent) with domain strings from ITEM-0018
- Domain string construction: `${appName}:${purpose}:v${version}`
- Unit tests proving purpose isolation and version isolation
- Integration test: same inputs produce same output on two separate Node process runs

## Out of scope

- Master key derivation from password — that is ITEM-0018 scope (Argon2id call)
- Per-device key wrapping — that is ITEM-0030

## Constraints

- Blocked by ITEM-0014 (interface), ITEM-0016 (encrypt/decrypt exist), ITEM-0018
  (domain strings must be committed before implementation)
- Must use the derivation primitive specified in ITEM-0018, not a custom construction

## Decisions and rejected alternatives

- Chose HKDF-SHA-256 info string over salt variation because salt is for entropy
  injection; purpose separation belongs in the info field per RFC 5869
- Rejected deriving subkeys directly from Argon2id output for each purpose because
  Argon2id is slow by design; it is called once to produce the master secret
