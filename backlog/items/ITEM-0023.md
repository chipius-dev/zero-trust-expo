# ITEM-0023: Implement account creation and login flows

## Why

Account creation and login are the entry points to the system. A bug here — leaking
the password in a request body, deriving the vault key server-side, or confusing the
password verifier with the encryption key — breaks the entire zero-trust model. The
implementation must match the flow documented in ITEM-0021 exactly.

## Scope

- `createAccount(password, accountMetadata): Promise<{ verifier, accountId }>`
- `login(password, verifier): Promise<AuthState>`
- `unlock(password, authState): Promise<CryptoUnlockState>`
- These are client-side functions; network calls are stubbed in tests
- Tests proving each acceptance criterion

## Out of scope

- Server endpoint implementation
- Password strength validation (UX concern)
- Password change flow — separate story under ITEM-0008

## Constraints

- Blocked by ITEM-0015 (hashPassword), ITEM-0019 (deriveSubkey), ITEM-0022 (auth
  protocol selected)
- Must match the sequence diagram from ITEM-0021

## Decisions and rejected alternatives

- Separated unlock from login because unlocking requires the password (to derive keys)
  but login may not need it (e.g., token refresh from persistent session)
- Rejected a single `loginAndUnlock` function because it prevents the app from
  maintaining an authenticated but locked state
