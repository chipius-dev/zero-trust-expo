# ITEM-0018: Document formal key hierarchy with domain-separated derivation contexts

## Why

Key hierarchy is an architectural decision that must survive developer turnover and
library changes. Without a committed document, each developer implements their own
derivation context strings — leading to incompatible derived keys across platforms
and across code changes. The document is also the reference for the threat model:
what does an attacker gain if they recover one subkey?

## Scope

- Markdown document in docs/architecture/key-hierarchy.md
- Full hierarchy diagram: Password → Argon2id → master secret → HKDF → per-purpose
  subkeys (vault, sync, attachment, device-wrap, recovery)
- Exact domain string for each purpose: format, uniqueness guarantee
- Per-key table: purpose, version, algorithm, derivation context, lifecycle rules,
  rotation trigger
- Worked example: show that vault-key-v1 and sync-key-v1 are distinct byte sequences

## Out of scope

- Implementation code — that is ITEM-0019
- Key persistence (device keychain, in-memory) — that is ITEM-0008

## Constraints

- Blocked by ITEM-0013 (library must be selected so derivation primitive is known)
- Domain strings must be globally unique within the application namespace
- Document body must stay under 120 lines per SDLC rule

## Decisions and rejected alternatives

- Chose a single Argon2id call to derive one master secret, then HKDF for all
  subkeys, over multiple Argon2id calls per purpose — Argon2id is deliberately slow;
  running it once per purpose is prohibitive on mobile
- Rejected using sequential integer contexts (0, 1, 2…) because they are opaque
  and version numbering collides with purpose separation
