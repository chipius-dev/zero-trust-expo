# ITEM-0013: Write ADR for cryptographic library selection

## Why

Without a committed ADR, the library selection lives only in chat history. Future
contributors cannot understand why the library was chosen, what was rejected, or
when it is appropriate to revisit the decision. The ADR is the link that survives
the context window.

## Scope

- Complete ADR using templates/adr-template.md, committed to docs/architecture/
- Record: chosen library, exact package name(s) and version(s), runtime support
  matrix, native/WASM dependencies, platform-specific limitations, maintenance
  status, security/audit history, and upgrade strategy
- Record all rejected alternatives with their specific disqualifying limitations
- Reference the ITEM-0012 compatibility matrix document

## Out of scope

- Implementation code — this story delivers a document only
- Choosing a secondary library if the primary covers all targets

## Constraints

- Blocked by ITEM-0012 (compatibility matrix must be complete before the ADR is written)
- ADR must follow templates/adr-template.md structure
- Decision must be reproducible: ADR must link the evidence (test scripts, matrix)

## Decisions and rejected alternatives

- Chose a committed ADR over a PR description because PR descriptions are hard to
  discover later and are not part of the codebase reference structure
- Rejected writing a PRD instead of an ADR because library selection is an
  architectural decision, not a product requirement
