# ITEM-0036: Implement threat model test scenarios for database compromise

## Why

The zero-trust guarantee is falsified if a database compromise test is never run.
Without machine-verifiable claims, the architecture is a set of promises that may not
hold in the implementation. Each threat in the threat model must have a corresponding
test that would fail if the threat materialised.

## Scope

- Threat model document: compromised database, malicious DBA, compromised backend,
  network attacker, replay attacker, credential-stuffing, offline password attack,
  stolen device, compromised device, malicious authenticated user, lost device,
  database backup theft
- Database-compromise test: populate schema with test data, query every table and
  assert no plaintext secret appears in any column
- Replay resistance test: assert that replaying an encrypted object write with a stale
  sequence number is rejected
- Document: per-threat, what attacker obtains, cannot obtain, and which security
  boundary prevents further compromise

## Out of scope

- Active red-team penetration testing
- Fuzzing the cryptographic library
- Third-party security audit

## Constraints

- Blocked by ITEM-0027, ITEM-0028, ITEM-0029 (schema complete) and ITEM-0025
  (pipeline complete)
- Threat model must list at least 13 threat categories per the architecture spec

## Decisions and rejected alternatives

- Chose machine-verifiable database tests over manual review because manual review
  cannot catch future regressions; a failing test does
- Rejected claiming threat model coverage without corresponding tests because an
  untested threat model is a document of intentions, not a security guarantee
