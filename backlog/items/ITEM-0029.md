# ITEM-0029: Define device sync event and revocation TypeScript types

## Why

Device names in the Device type immediately leak inventory information at the API
boundary. Plaintext fields in the SyncEvent type reveal application semantics. Without
a typed Revocation interface, device revocation and object deletion share no common
shape, making sync logic brittle. These types must be defined before any sync or
device enrollment code is written.

## Scope

- `Device` interface: `deviceId: OpaqueId`, `accountId: OpaqueId`,
  `publicKey: Uint8Array`, `wrappedVaultKey: Uint8Array`, `enrolledAt: number`,
  `revokedAt: number | null`
- `SyncEvent` interface: `eventId: OpaqueId`, `accountId: OpaqueId`,
  `sequenceNumber: number`, `encryptedPayload: Uint8Array`, `createdAt: number`
- `Revocation` interface: `revocationId: OpaqueId`, `targetId: OpaqueId`,
  `reasonCode: number`, `revokedAt: number`
- API contract types: `RegisterDeviceRequest`, `RegisterDeviceResponse`,
  `GetSyncEventsRequest`, `GetSyncEventsResponse`, `RevokeDeviceRequest`
- Local expo-sqlite DDL: `devices`, `sync_events`, `revocations` tables

## Out of scope

- Server SQL DDL
- Device name or human-readable label on any server-facing type
- Plaintext fields in sync event payloads — all semantic content is in
  `encryptedPayload`

## Constraints

- Blocked by ITEM-0027 and ITEM-0028 (preceding type definitions must exist)
- No device name on any server-facing type — the device name is application-layer
  content that lives inside the encrypted vault, not in the Device interface
- `reasonCode` on Revocation is a numeric enum, not a string description, to
  minimise semantic leakage

## Decisions and rejected alternatives

- Chose numeric `reasonCode` over a descriptive string enum for the revocation reason
  because string reasons leak semantics to any party observing the API
- Rejected storing device names in the Device interface; a human-readable label is
  a vault object encrypted under the vault key, not a server-visible field
