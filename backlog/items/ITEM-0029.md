# ITEM-0029: Design device registration sync events and tombstone schema

## Why

Device records, sync event logs, and tombstones each introduce potential metadata
leakage. A device table with a human-readable device name reveals the user's device
inventory. Plaintext sync event payloads reveal the application domain model. Without
a revocations table, deleted objects and revoked devices cannot be propagated to other
devices during sync.

## Scope

- `devices` table: device_id (opaque UUID), account_id, public_key (bytes),
  wrapped_vault_key (bytes, AEAD-encrypted to device public key), enrolled_at,
  revoked_at
- `sync_events` table: event_id, account_id, sequence_number, encrypted_payload (BLOB),
  created_at
- `revocations` table: revocation_id, target_id (device_id or object_id), reason_code,
  revoked_at
- Column-level privacy annotations

## Out of scope

- Device key generation — that is ITEM-0030
- Sync protocol implementation — that is ITEM-0033

## Constraints

- Blocked by ITEM-0027 and ITEM-0028 (preceding schema stories must be complete)
- Device name must not appear in any server-visible column
- Revocation must be represented by a tombstone row, not a DELETE

## Decisions and rejected alternatives

- Chose to store the wrapped vault key in the `devices` table (not in the objects
  table) because key transfer records have a different lifecycle than object ciphertext
- Rejected storing plaintext sync event summaries for server-side filtering because
  the server must not understand event semantics
