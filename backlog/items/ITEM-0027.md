# ITEM-0027: Design accounts and auth schema with opaque identifiers

## Why

The accounts table is the root of the data model. If it uses email addresses as
primary keys or has a username column, the database reveals the identity of every
user at rest. An opaque account_id with a separate hashed-email lookup row limits
what the database discloses even if fully exfiltrated.

## Scope

- `accounts` table: opaque UUID account_id, created_at, last_seen_at
- `auth_credentials` table: credential_id, account_id, credential_type,
  password_verifier (Argon2id hash), updated_at
- `sessions` table: session_id, account_id, device_id, issued_at, expires_at,
  revoked_at
- `schema_versions` migration table
- Column-level privacy annotations
- SQL indexes: justify each one; no index on any column that reveals user identity

## Out of scope

- Application-layer query code
- Encrypted objects schema — that is ITEM-0028
- Email lookup mechanism (one-way hash for lookup is an implementation detail,
  out of scope for the schema story)

## Constraints

- Blocked by ITEM-0021 (auth flow design must precede schema)
- Must be SQLite-compatible (no RETURNING, no JSON functions below SQLite 3.38)
- No sequential integer primary keys visible to the application or API

## Decisions and rejected alternatives

- Chose to store the password verifier in `auth_credentials` not `accounts` so that
  multiple credential types (future: passkey, recovery) share the account record
  without requiring schema migration to the accounts table
- Rejected storing email in `accounts` because email is an application-layer concept
  that enables user enumeration attacks
