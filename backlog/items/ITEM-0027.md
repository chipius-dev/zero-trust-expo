# ITEM-0027: Define account and auth credential TypeScript interfaces

## Why

Account and credential shapes are the entry point to every subsequent type. If the
Account type carries an email field, that field will propagate into every API call and
every local store row, revealing user identity at the API boundary. Defining the types
correctly first prevents the leak from spreading; fixing it later requires touching
every callsite.

## Scope

- `Account` interface: opaque `accountId: OpaqueId`, `createdAt: number`
- `AuthCredential` interface: `credentialId: OpaqueId`, `accountId: OpaqueId`,
  `verifier: PasswordVerifier`, `updatedAt: number`
- `Session` interface: `sessionId: OpaqueId`, `accountId: OpaqueId`,
  `deviceId: OpaqueId`, `issuedAt: number`, `expiresAt: number`
- API contract types: `CreateAccountRequest`, `CreateAccountResponse`,
  `LoginRequest`, `LoginResponse` — all with opaque IDs, no plaintext secrets
- Local expo-sqlite DDL as a typed constant: `accounts`, `auth_credentials`,
  `sessions` tables with opaque UUID primary keys and migration version table
- TypeScript unit: single entry-point export, no library types leaking through

## Out of scope

- Server SQL DDL — the server implements its own persistence independently
- Email lookup or username search logic
- Query helper functions — raw expo-sqlite DDL only

## Constraints

- Blocked by ITEM-0021 (auth flow must be designed before types are locked)
- No email, username, or any human-identifiable field on any server-facing type
- All ID fields must use the `OpaqueId` branded type, not plain `string`

## Decisions and rejected alternatives

- Chose branded `OpaqueId` type over plain `string` for ID fields to prevent
  accidentally passing a domain value (email, sequence number) where an opaque ID
  is expected — the type system catches the mistake at compile time
- Rejected a single `User` type combining auth and domain concerns because the
  auth layer must remain ignorant of the user's vault contents
