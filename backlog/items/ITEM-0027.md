# ITEM-0027: Define core domain entity TypeScript interfaces

## Why

Domain entity types are the shared vocabulary between every other layer. If they
are defined ad-hoc per feature, the same concept (Account, Device) accumulates
incompatible representations across the codebase. Defining them once, without
coupling to any storage or transport concern, gives every downstream story a stable
foundation to import from without triggering a cascade of changes when a field is
corrected.

## Scope

- `OpaqueId` branded type (string with a phantom brand — prevents passing a domain
  value where an opaque ID is expected)
- `Account`: `accountId: OpaqueId`, `createdAt: number`
- `AuthCredential`: `credentialId: OpaqueId`, `accountId: OpaqueId`,
  `verifier: PasswordVerifier`, `updatedAt: number`
- `Session`: `sessionId: OpaqueId`, `accountId: OpaqueId`, `deviceId: OpaqueId`,
  `issuedAt: number`, `expiresAt: number`
- `Device`: `deviceId: OpaqueId`, `accountId: OpaqueId`, `publicKey: Uint8Array`,
  `wrappedVaultKey: Uint8Array`, `enrolledAt: number`, `revokedAt: number | null`
- `Revocation`: `revocationId: OpaqueId`, `targetId: OpaqueId`,
  `reasonCode: number`, `revokedAt: number`
- Single entry-point export file; zero storage engine imports

## Out of scope

- SQL DDL, storage schema, or migration code of any kind
- Query helpers or repository patterns
- Device names or any human-identifiable field on any type

## Constraints

- Blocked by ITEM-0021 (auth flow must be designed before credential shape is locked)
- No field named `email`, `username`, `name`, `type`, or `label` on any type
- No import from any storage library

## Decisions and rejected alternatives

- Chose branded `OpaqueId` over `string` so the type system rejects accidental
  misuse (e.g., passing a sequence number as an account ID)
- Rejected bundling device name into `Device` — a human-readable label is application
  content that lives inside the encrypted vault, not in the type contract
